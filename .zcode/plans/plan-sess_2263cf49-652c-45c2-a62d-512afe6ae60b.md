# Detailed MCP approval prompts on TUI, Desktop, and Telegram

## Context

MCP tool-call approvals (trust gate / spend limit in `tools/mcp_tool_handlers.py::_ask_for_call`) already embed tool name, server name and redacted arguments into a free-text `message`, but that message is funneled through the generic **command-approval** pipeline (`command`/`description` payload fields, `pattern_key="mcp_elicitation"`). Every surface then renders it with command chrome: Telegram says "Hermes wants to run a command that needs your OK", Desktop labels it "Command" with a terminal icon, TUI titles it "approval required · <first line of description>". The details are an undifferentiated blob; arguments sit last (first to be cut by Telegram's budget) and are hard-capped at 1200 chars; the tool's own description (what it *does*) is never shown; the spend-limit branch omits arguments entirely.

Goal: MCP approvals render as **structured MCP tool-call approvals** — server, tool, tool description, redacted arguments — on TUI, Desktop, and messaging platforms (Telegram), while terminal-command approvals stay byte-identical.

Note for the user's own setup: your `mcp_servers` (linear, notion, clickhouse, posthog, sentry) have no `trust:` key → default `full` → the gate never fires for them in this tree. If you want per-call approval on those, set `trust: untrusted` per server in `~/.hermes/config.yaml`. This change makes those prompts detailed once they fire.

## Approach: structured context end-to-end

Thread one new optional payload key `mcp` through the existing approval pipeline. No new tool, no prompt-cache impact, no new env vars.

### 1. Core: build the context (`tools/mcp_tool_handlers.py`, `tools/mcp_tool_registration.py`, `tools/mcp_tool.py`)

- Add `_tool_descriptions: dict[Any, dict[str, str]]` in `tools/mcp_tool.py` (keyed like `_tool_read_only_hints`, connection key). Capture at discovery in `_record_tool_trust_metadata` (`mcp_tool_registration.py:76`): bounded (~400 chars), passed through the same redaction/control-char treatment as `_format_trust_gate_arguments` (server-controlled text is untrusted and lands on an approval card). Description is available on live, cache, and lazy paths (`t.description`; see line 421 area for the lazy annotations path).
- Parameterize `_format_trust_gate_arguments(args, max_chars=...)` (default stays 1,200 — the embedded-message copy is Discord-cap-constrained). New constant `_MCP_ARGUMENTS_CONTEXT_MAX_CHARS = 4_000` for the structured field; same masking/redaction pipeline.
- `_ask_for_call` builds and returns the context (both branches — spend limit gets arguments too; also append the `Arguments:` block to the spend-limit message text, matching the trust branch):
  ```python
  context = {"server": server_name, "tool": tool_name,
             "tool_description": _tool_description_for(server_name, tool_name),
             "arguments": _format_trust_gate_arguments(args, max_chars=4000) if args else None}
  ```
- `tools/approval_prompt.py::request_elicitation_consent` gains `context: dict | None = None`; the gateway branch sets `data["mcp"] = context` when present. Plugin hook kwargs (`pre_approval_request` etc.) unchanged — no hook-contract change.

### 2. tui_gateway wire (TUI + Desktop-over-WS)

- `tui_gateway/contracts/server_requests.py`: add a typed `ApprovalMcpContext` model (`server`, `tool`, `tool_description?`, `arguments?`) and `mcp: ApprovalMcpContext | None = None` on `ApprovalRequestParams` (the `tool_name` field stays untouched/unused).
- `tui_gateway/server.py::_approval_request_payload` copies queue-entry data — verify the new key rides along (contract is `extra="allow"`; explicit typing documents it). Re-redact the nested strings with `_redact_approval_command` at this display boundary, mirroring command/description handling.

### 3. Canonical gateway (Desktop event path)

- `gateway/session_pending_controls.py::PendingControls.register`: forward `data.get("mcp")` into the published `approval.request` prompt dict (redacted like the other fields).

### 4. ui-tui

- `ui-tui/src/app/createServerRequestHandler.ts` (`approval` case): read `p.mcp`, store on the overlay approval state.
- Type: add `mcp?: { server, tool, tool_description?, arguments? }` where the approval request/overlay types live (`gatewayTypes.ts` + overlay state).
- `ui-tui/src/components/prompts.tsx::ApprovalPrompt`: when `req.mcp` present, title becomes `⚠ approval required · MCP {server}/{tool}` (new i18n key in `src/i18n/en/overlays.ts`), tool description renders as a dim lead line, body lines = existing `approvalPreview`/`approvalWindow` machinery over the arguments (keep `v`-expand + paging). Non-MCP path unchanged.
- ui-tui tests: extend the `src/__tests__/approval*.test.ts` pattern for the MCP branch.

### 5. Desktop

- `apps/desktop/src/store/prompts.ts`: `ApprovalRequest` and `PendingApprovalPayload` gain `mcp?`; `receiveApprovalRequest`/restore path carries it.
- `apps/desktop/src/app/.../server-requests.ts` (`approval` handler) and `ui-tui/src/gatewayTypes.ts::CanonicalApprovalPrompt`: read/declare `mcp?`.
- `apps/desktop/src/components/assistant-ui/tool/approval.tsx`: when `request.mcp` exists, header row shows label "MCP tool call" (new i18n string in `apps/desktop/src/i18n/en.ts`), server · tool prominently, tool description as secondary text, arguments in the existing scrollable `<pre>` (max-h-40). Keep the `SYNTHETIC_COMMAND_RE` plugin-approval logic intact; terminal-command cards unchanged.

### 6. Messaging platforms (Telegram + shared base)

- `gateway/run_turn_runner.py::_render_approval_sync`: pull `mcp = approval_data.get("mcp")` and pass `mcp=...` to `adapter.send_exec_approval(...)`; same for the text fallback `_format_exec_approval_fallback`.
- `gateway/platforms/base.py`: `send_exec_approval` and `ExecApprovalPrompt` gain `mcp: Optional[dict[str, Any]] = None`; `_format_exec_approval` branches: with `mcp`, header becomes localized `MCP server '{server}' wants to run tool '{tool}'` (new catalog key `gateway.exec_approval.mcp_header` in `locales/en.yaml`; sibling locales fall back to en), fenced block = tool description line + arguments JSON (composed text goes through the existing `_ea_fit` platform budgets — Telegram UTF-16-after-escape fit keeps the card deliverable), reason line/deadline/smart-deny unchanged. Without `mcp`, output byte-identical to today.
- Wording accessor in `gateway/platforms/base_exec_approval.py` (`ea_mcp_header_text()`), mirroring `ea_header_text()`.
- Timeout-notice edit (`gateway/run_turn_runner_approval_settle.py`) composes from `command` — unchanged, still works.

### 7. Tests & checks

- Python behaviour tests (mirror tree; extend the existing trust-gate approval tests): payload carries `mcp` with server/tool/args; args redaction/masking applies to the 4k copy; `_format_exec_approval` MCP branch renders header + args and non-MCP branch unchanged; `PendingControls.register` forwards `mcp`; tui_gateway payload includes the context.
- TS: ui-tui approval prompt MCP render test; desktop store type/handler test if a pattern exists (follow existing test layout).
- Docs touched only where the payload is documented (grep `website/docs`, `AGENTS.md` files for the approval payload fields).
- Run `python scripts/check` and `scripts/run_tests.sh` (never bare pytest).
